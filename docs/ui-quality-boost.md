# 提升生成 UI 基础效果的方案

> 状态：**设计稿 + 数据依据**，尚未实施。实施记录另见 `docs/standards-report.md`。
> 目标不是「让生成更惊艳」，是**让默认输出不塌**——即使用户不传任何 skill、不写任何额外要求。
>
> 所有数字都来自本仓库实测，来源在每节标注。凡是没有实测支撑的判断，都标了「待测」。

---

## 一、问题定义

「基础款不好」不是审美判断，是五个可量化的缺口。任何一个单独出现都会让页面「看起来不对」，五个叠加就是现在的观感。

| # | 缺口 | 实测数据 | 来源 |
|---|---|---|---|
| 1 | **间距没有节奏** | `gap` 108 个里 **36 个（33.3%）** 不是 4 的倍数（值含 1/2/3/6/10/14） | 4 份真实 AI draft，305 节点 |
| 2 | **padding 同样散** | `padding` 408 个里 **56 个（13.7%）** 不是 4 的倍数（值含 2/5/6/10/14/18/22） | 同上 |
| 3 | **页面是平的** | 不带 skill 时**阴影节点 0 个**；带 skill 后**仍是 0 个** | 附录 A |
| 4 | **配色本身有问题** | 对比度违例 **406 条**（25 页 × 2 端 / 2266 节点，8.12 条/页） | `docs/standards-report.md` S4 |
| 5 | **字段用不起来** | 样式字段覆盖 **8/37**，带 11.7K 字符 skill 后**零变化** | 附录 A |

**关键结论：这五条没有一条能靠 skill 修。** 原因不是 skill 不够好，是位置不对——skill 在模型之前，这五条要么发生在模型之后（转换层），要么根本不在模型的控制范围内（`gap` 是 token 序列里随机漂出来的，不是「决定」出来的）。

## 二、三条杠杆（按性价比排序）

### 杠杆 1：转换层默认值（收益最大）

**思路：模型不写，就给好的默认值。** 现在是「不写就没有」，所以模型一偷懒页面就塌。

| 原计划 | 现状 → 改为 | 2026-11-01 实测结论 |
|---|---|---|
| 阴影 | 有背景的 FRAME 没写阴影 → 平的 | 自动补最小阴影 | **撤销**：32 个卡片候选里 24 个已有阴影，剩 8 个中 5 个是品类列表项（本不该有阴影）。附录 A 的「阴影 0 个」是 2026-10-28 数据，那时还没加 `styleRecipeBlock` |
| 间距 | `gap` 写 7 → 原样输出 | 吸附到最近 4 倍数 | **降级**：每页 gap 只有 2-6 种值，不算散；`14` 是高频值但改它用户看不出来。4 倍数规则本身过严（`gap:2` 是图标与文字的合理紧凑值） |
| 对比度 | 正文 3.1:1 → 原样输出 | 加深到 ≥4.5:1 | **收窄**：83 条 <3.0 里 50 条是 `#999` 次要文字（设计选择），只做 <1.5 的「几乎不可见」 |

**为什么这是最大杠杆**：它把「质量」从「模型这次有没有心情写」变成「不管怎么写都兜住」。这正是确定性编译器相对纯模型生成的核心优势。

**代价**：像素会变。`gap: 3 → 4` 是 1px 位移。商城 6 页的 100% 会掉到 99.x%。
**这个代价必须接受**——像素 100% 只能证明「产物 = 设计」，设计本身节奏乱时，100% 是假绿。

### 杠杆 2：few-shot 扩充（最快见效）

附录 A 的结论原文：

> **「差距主因是 few-shot 没教」** —— few-shot 是**同格式的示范**（`{"kind":"FRAME","style":{"effects":[...]}}`），skill 是**自然语言的期望**（「阴影要克制」）。前者教「怎么写」，后者只说「要什么」。**模型缺的是前者。**

现在 `fewshots.json` 只有 2 个样例进提示词。扩充到 5 个高质量样例，成本是一次性的（进 `system` 稳定前缀，吃 prompt cache）。

**但要注意预算**：稳定前缀现在是 **11363 / 12000 tokens，只剩 637 余量**。加 few-shot 必须先删别的（`RULES_BLOCK` 里和 few-shot 重复的部分可以删）。

### 杠杆 3：软规则搬成硬检查（收尾）

`RULES_BLOCK` 规则 2 已经写了「padding/gap 用 4 的倍数」，模型 33% 不遵守，转换层零拦截。

**这条规则目前是纯装饰**——写在提示词里，没有执行机制，也没有检测。要么搬进转换层（杠杆 1），要么删掉省 token。**留着不管是最坏的选择**：它让「我们有这个规范」变成一句空话。

## 三、反 bug 规则库

### 设计原则

1. **只防「实际扫出来过」的 bug**，不凭想象加规则（`scripts/ui-audit.ts` 负责扫）
2. **规则住转换层**（`specToPage` 的 normalize 系列），不住提示词——提示词可以被无视，代码不能
3. **每条规则必须能证明「撤掉会变红」**，否则不算修完
4. **修复要静默**：能改对就改对，不报违例（报违例=多烧一轮，产物一样）

### 已有 4 条（模板）

| 规则 | 防的 bug | 位置 |
|---|---|---|
| `normalizeAbsolute` | 绝对定位容器缺 HUG → 高度塌 0 | `specToPage.ts:762` |
| `normalizeFill` | FILL 用在错误位置 | `specToPage.ts:922` |
| `normalizeGridItems` | 等分网格里 HUG 子项 → 横向溢出 | `specToPage.ts:965` |
| `normalizeHugSize` | HUG + 固定尺寸 → 出 7×12 竖条 | `specToPage.ts:1254` |

### 已实施 2 条（2026-11-01）

| 规则 | 判据 | 动作 | 实测 |
|---|---|---|---|
| `normalizeInvisibleText` | 文字色与**可判定背景**对比度 < 1.5 | 换成黑或白（按背景亮度） | 商城 6 页改 **1 处**：`#CC785C on #1677FF` → 白字 |
| `normalizeSticky` | 有 `position:'FIXED'` 且贴底（`y+h≥视口高-2` 或 `stickyBottom===0`）的元素，根容器 `padding-bottom` < 其高度 | 补到该高度（保留其余三边） | 2 处：商品详情底栏 64px、点菜小程序购物车栏 68px |

**`normalizeInvisibleText` 阈值取 1.5 而不是 4.5**：25 页扫描里 50 处是 `#999999` 压白底（2.85:1），那是刻意的次要文字；
自动加深会改掉「辅助信息的视觉重量」，属于改设计。1.5 以下才是**几乎不可能有意为之**。

**`normalizeSticky` 的像素代价是零**：`padding-bottom` 只影响可滚动范围的底部，视口顶部截图完全不变。
换句话说 `npm run diff` 那 19 页 / 商城 6 页**根本看不见它** —— 这正是它必须靠结构判据发现的原因，
也是「像素 100% 只能证明产物 = 设计，不能证明设计 = 意图」的又一个实例。

**三条误报防线**（每条都配了 pass 测试）：
1. 渐变 / 图片 / 半透明背景 → `ownBackground` 返 `unknown`，整个子树跳过
2. 背景画在**同级绝对定位层**上（demo「13 绝对定位页」的海报结构）→ 跳过
3. 深色底白字、深灰底中灰字（3.3:1）→ 不动

> **防线 2 曾经是失效的（2026-11-01 审计发现）。** 第一版 `hasBackdropLayer` 要求背景矩形
> `position === 'ABSOLUTE'`，而 demo 里那个矩形**没有 position 字段** —— 它靠父容器的
> `mode: 'ABSOLUTE'` 天然脱流。于是这条判定永远返回 `false`，写了却从未生效。
> 之所以一直没暴露，是因为 `build-pages.ts` 走 `compilePage` 不经过 `normalizePage`。
> 是 `bugscan` 的 `text-invisible` 在 demo 上报出 3 条误报才把它揪出来的 ——
> **「写了防线」和「防线在跑」是两件事，只有独立检测器能验证后者。**

**测试**：`tests/ai-invisible-text.test.ts`（13 用例）+ `tests/ai-sticky-padding.test.ts`（11 用例）。
撤掉 `normalizePage` 里对应那一行 → 分别 **6 个 / 6 个**用例变红，均已验证。

### 待加 6 条（已被审计扫过，按实测决定做不做）

**2026-11-01 实测：9 个检测器跑在 37 页 / 2023 节点上（demo 19 + mall 存量 6 + mall 重跑 6 + draft 6）。**
完整数据见 `docs/ui-audit-report.md`，这里只留结论。

| # | 规则名 | 实测命中 | 决定 |
|---|---|---|---|
| 1 | `normalizeBadge` | **0**（已被 `normalizeAbsolute` 规则 4 覆盖） | **不需要新写**，检测器留作回归基线 |
| 2 | `normalizeSticky` | **2**（商城商品详情 64px / 点菜小程序 68px，`padding-bottom` 都是 0） | ✅ **已实施**（见 §三「已实施」） |
| 3 | `normalizeVectorRatio` | 1（电量图标 viewBox 24×24 → 渲染 18×14） | **不做**：只有 1 处，改尺寸会动布局，收益不抵风险 |
| 4 | `normalizeTextOverflow` | 0 | **不做**：产物里没有这种形态 |
| 5 | `normalizeSameColor` | 0（已被 `normalizeInvisibleText` 覆盖） | **不需要新写**，检测器留作回归基线 |
| 6 | `normalizeEmptyFrame` | 0 | **不做**：产物里没有这种形态 |
| 7 | `normalizeGapRhythm` | 1（点菜小程序 7 种 gap） | **不做**：整页只有 1 处，且「档数多」不等于「难看」 |

**这一轮的结论比规则本身值钱**：7 条候选里，**只有 1 条真的需要写**。另外 2 条已经被既有 normalize 覆盖（说明之前的修复在跑），4 条在真实产物里根本不存在。

### 检测器与规则的区别（为什么要有 `bugscan/`）

`src/editor/ai/bugscan/` 只**检测**不修复，`specToPage.ts` 的 `normalize*` 只**修复**不检测。
分开的理由：先拿到「有哪些 bug、各多少条」的数据，再决定写哪条规则。混在一起就会变成
「想到一条写一条」，而实测证明这条路有一半是无效的。

检测器还有一个长期价值：它是**回归基线**。`badge-inline` 永远是 0 命中不是因为它没用，
而是因为 `normalizeAbsolute` 规则 4 在跑；哪天有人动了调用顺序，它会立刻从 0 变成 N。

### 两条明确不做的

- **不做「自动美化」**：比如自动加渐变、自动调整字号阶梯。那属于「改设计」，超出反 bug 范围，且没有客观判据。
- **不做「构图优化」**：AST 连构图字段都没有（见 §五），无从下手。

## 四、验证方案（两层，缺一层就是假绿）

### 第一层：规则本身（变异测试）

每条规则必须配三件套：

1. **fail fixture**：一个含该 bug 的最小页面 → 断言被修好
2. **pass fixture**：一个正常页面 → 断言**不被改动**（防误伤）
3. **变异测试**：把 `check` 换成 `() => []` → 反例必须变红

第 2 条最容易被跳过，但它是「误伤」的唯一防线。`normalizeHugSize` 第一版按轴分别转，就把分类页品类栏 `HUG+width:92` 转成 FIXED（宽 16px），挤窄了右侧网格——**pass fixture 能抓到，fail fixture 抓不到**。

### 第二层：真实产物（场景审计）

`npm run ui:audit` → `docs/ui-audit-report.md` + `docs/ui-audit-baseline.json`。

**已落地的是「存量扫描」，不是「场景生成」。** 两者都要，但顺序不能颠倒：

| 模式 | 状态 | 扫什么 |
|---|---|---|
| 存量扫描 | ✅ 已实现 | demo 19 页 + 商城 6 页 + 6 份真实模型 draft，共 37 页 / 2023 节点 |
| 场景生成 | ✅ 2026-11-01 已跑 | `scenarios.ts` 的 45 个场景逐个调模型，产物存 fixture 再扫（45/45，1786 节点） |
| 渲染量测 | ✅ 2026-11-01 新增 | `npm run ui:measure`：读渲染后的盒子，6 类判据（结构扫描查不出的那几类） |

**「存量扫描够用」这个判断被证伪了。** 拿到 key 之前我认为 6 份真实 draft 已经能回答
大部分问题；实跑 45 场景后，最贵的两个 bug（图标占位符被闸门拒 → 20% 页面整页失败、
`HUG` 吞显式高度 → 底栏 40px）在存量 6 份里**一个都没出现**。
原因很直接：存量那 6 份是「同一条提示词生成的 6 页」，形态高度重合，而 45 场景是
按「前端可能出现的 UI 形态」横向铺开的。

**结构扫描同样不够**：`bugscan/` 读节点树，上面两个 bug 在 AST 里完全合法。
所以第三层验证是**量渲染结果**，不是再补几个检测器。

**为什么必须先扫后写规则**：这一轮 7 条候选里只有 1 条真的需要写，
另外 4 条在真实产物里根本不存在、2 条已被既有 normalize 覆盖。
凭经验列规则的话，那 6 条会全部写完，然后一条都不起作用。

**两层都要有，因为**：
- 第一层证明「规则写对了」
- 第二层证明「规则防的是真 bug」

只有第一层，规则可能防的是一个从没发生过的 bug；只有第二层，修完没有回归保护。

### 第三层（本轮新增）：demo 归零 = 误报防线

`demo` 那 19 页是**人工设计**的，里面不该有形态 bug。所以判据是：

> **demo 组命中 > 0 就是误报，必须先修检测器再谈其它。**

这一条不是理论：`text-invisible` 第一版在 demo 上报了 3 条，
查下去发现 `hasBackdropLayer` 的判据写错、那条防线从未生效（详见 §三）。
如果没有这层，那 3 条会被当成「demo 也有 bug」，然后白写一条没用的规则。

## 五、明确做不到的（边界）

| 做不到 | 原因 | 影响 |
|---|---|---|
| **真实图片** | AST 的 IMAGE 只有占位色块（`imagePlaceholder` 按名字哈希出颜色） | 「第一眼惊艳」主要来自图片，这块补不上 |
| **内容密度** | 模型主动压缩（附录 A 实测 118 → 92 节点） | 页面看起来「空」 |
| **创意构图** | AST 无构图字段，只有 `mode` / `gap` / `padding` 三种排布手段 | 做不出「不对称」「错位」这类设计手法 |
| **精细视觉特效** | `::before` / `mix-blend-mode` / `clip-path` 无对应字段 | 只有阴影、模糊、渐变、描边四种 |
| **多端一致的精修** | 只有 H5 有像素通道，小程序端只做结构断言 | 小程序端视觉问题靠人看 |

**这不是「以后能补」，是架构边界。** 承认它的意义在于：不要拿「不如 Stitch」当失败——Stitch 出完整 HTML + 真实图片，你出 AST + 占位色块，第一眼本来就不在同一个量级。

**能比的是另外三件事**：每次生成质量稳定（不靠模型运气）、可逐字节复现、可验证（像素 + 规则 + 变异测试）。

## 八、S4 实跑：45 场景 + 渲染量测（2026-11-01）

拿到真实 key（千问平台 `deepseek-v4.1-flash`，¥1/¥4 per MTok）后第一次跑通全链路。
**这一步推翻了两条此前的判断**，值得单独记。

### 8.1 数字

| 项 | 结果 |
|---|---|
| `ai-matrix` 实跑档 | **13/13 通过**；B1 一次通过率 80%、B2 自修后 100%、均 **¥0.011/页** |
| 45 场景生成 | **45/45 成功**，首轮通过 29（64%），合计 **¥0.216**，2 分钟（并发 2） |
| 45 页节点 | 1786 个（均 40 个/页） |
| 量测命中 | 65 → **18**（先修掉检测器自身误报，见 8.4） |

### 8.2 修掉的两个真 bug

**① 图标占位符被闸门拒 → 20% 页面整页失败（最贵的一个）**

`repeat` 里让 N 个图标各不相同的**唯一**写法是 `icon:"{{icon}}"` + `values.icon:[...]`。
但 `contract.ts` 的闸门跑在**展开之前**，此刻 `spec.icon` 还是字面量 `"{{icon}}"`，
拿去查图标表必然查不到 → 报违例 → 模型连改 3 轮（它写的就是标准写法，改不出来）→ 抛异常。

实测 `ai-matrix` 10 页里 L3/L6 两页全挂在这条上，**B2 从 100% 掉到 80%**。
修法分两层：闸门放行 `{{...}}`（检查挪到能判的那一层），转换层拿到替换后的真名再查；
真名仍无效时**降级成相近图标 + `autoFixed` 违例**（不判失败——一个图标不值得烧掉整页）。

**② `HUG` + 显式高度 → 声明值被吞，底栏被压扁**

编译层把 `HUG` 译成 `height: fit-content`，显式 `height` **整个丢掉**。
模型的习惯写法是「底栏 `height:64` + HUG」，于是底栏真的只剩内容高（实测 **40px**）：
20px 图标 + 14px 文字挤满，文字底边落在视口第 **811** 行（视口 812）——
看起来就是「底栏文字被切了一半」，而**像素比对、结构断言、AST 扫描全都查不出**。

修法：`normalizeHugSize` 给 `min-height` 地板（内容矮时按声明值，内容高时照常撑开）。
**只做高度轴**，宽度轴有历史回归（品类栏 `HUG+92` 落成固定宽会挤窄商品网格）。

### 8.3 还剩的三类（下一批）

| 类 | 命中 | 典型 | 为什么没顺手修 |
|---|---|---|---|
| 按钮文案折行 | 11（2 页） | 「加入购物车」挤进 86px 盒子 → 2 行 | 改法有取舍：加宽 / `textWrap:false` / 降字号，都会动布局，需要单独验一轮 |
| 横滚列表子项被压到 33px | 9（1 页） | 5 张卡在横滚行里各 33px，标题折 3 行 | 与「等分网格 HUG→FILL」同源，改之前得先确认横滚容器的主轴语义 |
| 子项超出父盒 | 4（2 页） | 骨架卡内容 355 > 盒宽 341 | 多为 `FILL + padding` 双算，属布局引擎侧，不在 AI 转换层 |

### 8.4 工具与方法（这次新增）

| 脚本 | 作用 | 关键设计 |
|---|---|---|
| `scripts/ui-gen.ts` | 45 场景 → 真实模型 → 落 draft + page | `--rebuild` 不调模型、只重跑 `draftToPage`：**同一份输入过新旧两版转换层**，才可比 |
| `scripts/ui-shots.ts` | 逐页截图 + 3×3 联系表 | 联系表用浏览器自己排版打标签，比手工拼 PNG 省事 |
| `scripts/ui-measure.ts` | 读**渲染后的盒子**，6 类判据 | 见下 |

**量测脚本踩的两个坑（都属「误报比漏报更贵」）**：

1. 第一版用「高度 ÷ 行高」判折行 → 39 条里 30 条是**按钮的上下 padding**被当成第二行。
   改用 `Range.getClientRects().length` 数**真实行盒**，误报归零。
2. 第一版把「流内元素落在 812 以下」全判成 bug → `card-badge`（页高 963）里正常滚动的文字
   被记了 18 条。改为**只判 `fixed/absolute` 祖先链**：流内元素在视口外就是该滚。

**核心教训**：`bugscan/` 那 9 个检测器读节点树，判据只能是「字段组合像不像 bug」；
而这次抓到的两个真 bug（底栏贴边、按钮折行）**在 AST 里完全合法**。
判「生成的东西有没有坏」必须**量渲染结果**，结构扫描只是第一道筛子。

## 七、一句话总结

**基础效果的天花板由 AST 的表达能力决定，地板由转换层的默认值决定。** 这一轮能抬的是地板——把「模型这次写得好不好」变成「不管怎么写都不塌」。天花板动不了，那是架构问题。

**这一轮真正交付的不是那条规则，是「先扫后写」这套流程。** 两轮实测都指向同一个结论：
凭经验列的规则一半以上无效。有了检测器，判断「该不该写」从主观变成看数字。
